# Part 3: Production Incident Investigation — 502 Bad Gateway

## What a 502 actually means

A `502 Bad Gateway` means the component acting as a **proxy** received a request,
forwarded it to the next component in the chain, and got back either **no
response**, a **broken/invalid response**, or a **refused connection**. A 502 is
never generated by the thing that's actually broken — it's generated by
whichever proxy sits in front of it and couldn't get a good answer back.

In this architecture there are **two possible places** a 502 can be generated,
because there are two proxy hops between the user and the application:

```
User → ALB (proxy #1) → Nginx (proxy #2) → Gunicorn (application)
```

| Who returns the 502 | What it means |
|---|---|
| **The ALB** | The ALB couldn't get a valid response from **Nginx** on the target instance — Nginx is down, the instance failed its health check and was deregistered, or the security group blocks port 80 |
| **Nginx** | Nginx is fine, but it couldn't get a valid response from **Gunicorn** over the Unix socket — Gunicorn isn't running, crashed, isn't listening on the expected socket, or the socket has a permission problem |

Distinguishing which of the two returned the 502 is the first thing to check,
since it immediately narrows down where to look.

## Step 1 — Which proxy returned the 502?

```bash
curl -sI https://app.example.com/
```

- A response with an `Server: awselb/2.0` header, or a plain generic error page
  with no Nginx branding → the **ALB** generated it (Nginx never responded to
  the ALB's request, or the target was already deregistered).
- A response with `Server: nginx` → **Nginx** generated it (Nginx is up and
  answering, but couldn't reach Gunicorn).

Also check target health directly:

```bash
aws elbv2 describe-target-health --target-group-arn <tg-arn>
```

If a target shows `unhealthy` or `draining`, the ALB has already stopped
sending it traffic — that instance is confirmed to be the problem, and the ALB
is correctly routing around it (assuming at least one other instance is
healthy). If **all** targets are unhealthy, the whole fleet is affected — check
for a recent deploy first (see Step 8).

## Step 2 — Service status on the instance

Connect via **SSM Session Manager**:

```bash
aws ssm start-session --target <instance-id>
```

```bash
sudo systemctl status app-gunicorn nginx --no-pager
sudo systemctl is-active app-gunicorn nginx
sudo nginx -t                     # confirm the Nginx config itself is valid
```

## Step 3 — Nginx logs

```bash
sudo tail -n 100 /var/log/nginx/app.error.log
sudo grep ' 502 ' /var/log/nginx/app.access.log | tail
```

| Nginx error line | Meaning |
|---|---|
| `connect() to unix:/run/app/gunicorn.sock failed (2: No such file or directory)` | Gunicorn isn't running, or the socket path is wrong |
| `(13: Permission denied)` | Nginx (`www-data`) can't access the socket or a directory in its path |
| `(111: Connection refused)` | The socket file exists but nothing is listening — process crashed after creating it |
| `upstream prematurely closed connection` | A Gunicorn worker crashed or was killed (often OOM) mid-request |
| `upstream timed out (110)` | The app is hanging — slow DB query, deadlock, or the app-side timeout is too low. Usually shows as 504, occasionally 502 |

## Step 4 — Application logs (Gunicorn / Django)

```bash
sudo journalctl -u app-gunicorn -n 200 --no-pager
sudo journalctl -u app-gunicorn --since "30 min ago" | grep -Ei "error|traceback|critical|worker|boot"
sudo journalctl -k | grep -Ei "oom|killed process"     # OOM killer activity
```

Look specifically for: `ModuleNotFoundError`, `ImproperlyConfigured`, a
`KeyError` on a missing environment variable, `OperationalError` (database),
or `Worker failed to boot`.

## Step 5 — Port, socket, and process checks

```bash
ps aux | grep gunicorn              # is the master process + workers alive?
sudo ss -xlp | grep gunicorn          # is the Unix socket actually listening?
ls -l /run/app/                       # does the socket file exist? who owns it?
curl -v --unix-socket /run/app/gunicorn.sock -H "Host: app.example.com" http://localhost/healthz
sudo ss -ltnp | grep :80              # is Nginx listening on 80?
```

If curling the socket directly works but Nginx still returns 502 through the
browser → the problem is in Nginx's config or permissions. If the socket curl
itself fails → the problem is in the application/Gunicorn.

## Step 6 — Permission checks

```bash
namei -l /run/app/gunicorn.sock              # every directory in the path must be traversable
sudo -u www-data test -r /run/app/gunicorn.sock && echo "readable by nginx" || echo "NOT accessible by nginx"
ls -ld /opt/app /opt/app/current /opt/app/shared
ls -l /opt/app/shared/.env                    # must be readable by the 'app' user
id app; id www-data
```

This matters here specifically because Gunicorn runs as `app` and Nginx runs as
`www-data` — a socket permission mismatch (wrong `--umask`, wrong `Group=` in
the systemd unit) is one of the most common causes of a 502 after a config
change.

## Step 7 — Reproduce by hand

```bash
sudo -u app bash -c 'set -a; . /opt/app/shared/.env; set +a; cd /opt/app/current && ./venv/bin/python manage.py check'

sudo -u app bash -c 'set -a; . /opt/app/shared/.env; set +a; cd /opt/app/current && ./venv/bin/gunicorn config.wsgi:application --bind 127.0.0.1:9000'
```

Running Gunicorn manually in the foreground surfaces import errors, missing
environment variables, or a database connection failure directly in the
terminal — much faster than digging through logs.

## Step 8 — Resources and dependencies

```bash
df -h; df -i                          # disk or inode exhaustion
free -m; uptime                       # memory pressure / load average
psql "$DATABASE_URL" -c "select 1"    # is RDS actually reachable from this instance?
aws rds describe-events --duration 120   # recent RDS failover/maintenance events
```

## Step 9 — Restoring service safely

1. **Check whether this followed a deploy.** Compare the incident start time
   against the last Jenkins pipeline run. If they line up, prefer rollback over
   live debugging on production.
2. **Roll back:**
   ```bash
   sudo /opt/app/bin/rollback.sh
   ```
   This is the same script the Jenkins pipeline calls automatically on a
   failed deploy (Part 2) — it can also be run by hand over SSM Session Manager
   at any time.
3. **If it wasn't a deploy** (e.g. a resource exhaustion or an RDS event), fix
   the specific cause directly — restart the service, clear disk space, wait
   out an RDS failover — rather than rolling back code that wasn't the problem.
4. **Verify:**
   ```bash
   curl -fsS https://app.example.com/readyz
   aws elbv2 describe-target-health --target-group-arn <tg-arn>
   ```
   Confirm the target group shows all instances `healthy` and a real user flow
   works, not just the health endpoint.
5. **Post-incident:** write a short RCA, and if the root cause wasn't already
   caught by `deploy.sh`'s own health check or a CloudWatch alarm, add the
   missing safeguard so the same failure is caught automatically next time.
